# Toolkit refactoring plan

Status: approved on 2026-09-19. Phase 0 is done: the harness and the baseline snapshots are in `tests/`, and the Code Editor round is in [code-editor-checklist.md](code-editor-checklist.md).

## Why

The nine toolkits add up to about 26,000 lines, and most of that is the same engine copied into each script:

- **Duplicated engine.** 19 functions appear in seven or more scripts: `loadTablesNames`, `loadFeature`, `makeLayersList`, `export2Drive`, `calculate`, `formatName`, `tableShortName` and others. Every fix has to be applied nine times.
- **Data mixed with code.** Collections, territories and palettes live inside `App.options` (about 134 KB in `lulc`, 68 KB in `fire`), and they are updated by patching the scripts.
- **Hard-coded download links.** 456 in `lulc` (behind a disabled tab, many broken) and 913 in `fire`.
- **Dependencies on personal GEE accounts.** `users/joaovsiqueira1/packages` (Mapp, Legend) and `users/workspaceipam/packages` (fire palettes and logos).
- **Collection-specific branches.** Class encoding, band names and legends that differ per collection are handled case by case, in different ways in each script.
- **Deprecated API.** The "own territory" feature relies on `ee.data.getAssetRoots()`, which the Code Editor flags as deprecated.

## Decisions

| Topic | Decision |
|---|---|
| Where the shared code lives | In this same public repository (`users/mapbiomas/user-toolkit` and its GitHub mirror). Public access to everything MapBiomas produces is a principle. |
| Download tabs | Replaced by a link to the MapBiomas download page of each region. |
| Export names and CSV columns | Standardized across all toolkits. This is announced as a breaking change. |
| Scope | All nine toolkits: lulc, deforestation-regeneration, fire, water, irrigation, mining, pasture, soil, degradation. |

## Target layout

```
mapbiomas-user-toolkit-<theme>.js   entry points, at the root (users keep opening the same files)
core/v1/app.js                      panel flow: region → collection → territory → property → feature → data type → years
core/v1/territory.js                official territories, the user's MAPBIOMAS folder, buffer
core/v1/layers.js                   class decoding (encoding, band renames, transition remap), palettes, SLD
core/v1/export.js                   GeoTIFF + area CSV with standard names and columns
core/v1/ui.js                       logo, links, legend panel (no dependency on personal packages)
data/<theme>.js                     generated: collections, territories, palettes, legends, download pages
```

- An entry script only declares its theme: data types, band prefixes, decoding and legend. The behavior lives in `core/`.
- `core/` is versioned by folder. A breaking change goes to `core/v2/`, and each toolkit moves over once it is tested.
- `data/<theme>.js` is generated by the maintenance tools and replaces the patching of `App.options`.
- Everything stays ES5, because that is what the Code Editor runs.

## Phases

### Phase 0: safety net (no behavior change)
- A test harness in `tests/` loads each toolkit in Node with mocked `ee`, `ui`, `Map` and `Export`. It walks the panel flow (region → collection → table → property → feature → data type → layer → export) and records what the user would see and get: region and collection lists, data types, layer names, and the parameters of every export task.
- It saves a baseline snapshot of every toolkit in `tests/snapshots/`. The refactored code has to reproduce it, except where Phase 4 standardizes names on purpose.
- A manual checklist for the Code Editor covers what the mocks can't: map rendering, legends and real tasks. The round of 2026-09-19 is in [code-editor-checklist.md](code-editor-checklist.md): all nine toolkits rendered and all 18 export tasks reached `SUCCEEDED`.

### Phase 1: extract the core
- Start with pure helpers (area table, class decoding, naming), then the panel flow.
- Migrate from the simplest toolkit to the most complex: pasture → irrigation → mining → water → deforestation-regeneration → lulc.

### Phase 2: data out of the code
- The maintenance tools generate `data/<theme>.js` instead of patching `App.options`.
- Collection-specific branches become flags in the data: `encoding`, `legend`, `bandPrefix`.

### Phase 3: dependencies and cleanup
- Bring `Mapp`, `Legend` and the fire palettes and logos into `core/`.
- Replace `ee.data.getAssetRoots()` with a listing of the `MAPBIOMAS` folder in the user's Cloud project, and allow pasting a table path.
- Remove commented-out code and the hard-coded download tabs. Add the link to each region's download page instead.

### Phase 4: special themes and standardization
- Move fire (monthly monitor, disclaimers), soil and degradation (beta modules) onto the core.
- Standardize the buffer, the area CSV (same columns everywhere), the export names and the legend panel. Document the changes as breaking.

### Phase 5: release
- Publish toolkit by toolkit, keep the previous scripts in `legacy/` for a transition period, and add a changelog to the README.

## Findings so far

- **Phase 0, production bug:** in deforestation-regeneration, picking a territory in collections that lack `deforestation_pv` (Brazil C11, Peru C4, Bolivia, Uruguay, Paraguay, Argentina) threw an error. Fixed in 1.7.3.
- **Things the snapshots show for Phase 4:** export names differ between toolkits (fire: `mapbiomas_brazil-fire_monitor-…-feature_a`; the others: `mapbiomas-brazil-collection-110-featurea-…`). Layer names also differ: some use the feature name, others the table name.

## Risks

- **People who post-process exports.** The standard names and CSV columns will break their scripts. The change is announced in the changelog, and the old scripts stay in `legacy/` for a while.
- **`require` always loads the latest code.** A bug in `core/` would reach every toolkit at once, which is why `core/` is versioned by folder.
- **The UI only runs in the Code Editor.** The harness covers data and flow, and the manual checklist covers rendering.
